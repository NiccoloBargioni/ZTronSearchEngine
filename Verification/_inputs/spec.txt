1. Scope and goals
ZTronSearchEngine is a Swift package for fully offline, typo-tolerant, multilingual search
over heterogeneous items, plus a SwiftUI search field with native search tokens. It targets
an iOS 15.0 deployment floor, Swift 6 strict concurrency, and must stay fast on an iPhone
6s.
Goals:
Fully offline: no network at query time; indexes and item vectors ship with the app or
are built at sync time.
One engine for tools, tips, maps, games and captioned images, with kind-aware
ranking; every hit reports which class it came from. The host decides the search
context programmatically: independent, disjoint contexts with their own schema,
from the whole catalog down to a 20-item picker (section 9.1). Items may live in
memory or in a SQLite database reached only through a host-injected boundary, with
string expressions that hold either the text itself or a localization key (section 9.2).
Semantic and cross-language retrieval through a shared multilingual embedding
space.
Typo tolerance with bounded edit distance.
Internationalized content: the engine indexes and matches localized values whenever
an item provides them, and falls back to base values otherwise.
Throttled, cancellable search that never publishes stale results.
Testable and memory-conscious on a 2 GB device, with grounded chat over the
corpus through a local LLM on devices that can run one, reached only through host-
injected boundaries (section 14).
Non-goals:
Online or server-side search, and cloud LLMs.
A cross-encoder reranker or a local LLM on the reference device; devices that pass
the gates in sections 7.4 and 14.4 run them.
Pixel-level image understanding: images are searched through caption, alt text, tags
and OCR text.
Personalization logic: the engine exposes a hook only.

3. Core principle: evidence versus weight
A Searchable provides evidence; the search engine decides weight. Everything beyond
identity and text is an optional capability, and everything about weight lives in
RankingProfile and the signal providers the host injects.
The domain object must not own:
BM25 or semantic scores
final ranking weights or popularity boosts
query-dependent relevance
index implementation details, including field weights, vector format and persistence
layout
Consequences that bind the design: domain types never import the engine's index types;
the projection (section 6) is the only engine-side view of an item; and ranking can be
retuned by swapping a RankingProfile without touching a single domain type.
4. Domain contracts
Three members are required, identity, kind and text; every other capability is an optional
protocol the engine detects by conformance at projection time.

4.1 Typed kinds and filters
The engine is generic over one SearchSchema the host declares: its Kind enum names
the classes of items (map, tip, tool, game, image) and its Filter enum names the filters.
Every hit, query, token and snapshot speaks in those two enums, checked at compile time,
and the string design from the original document survives as the fallback schema.
public protocol SearchSchema: Sendable {
    associatedtype Kind: SearchItemKind
    associatedtype Filter: SearchFilter
}

    var key: String { get }                 // dimension; stable across app

Rules:
One schema per engine instance, fixed at construction: SearchService<Schema> ,
SearchQuery<Schema> , SearchHit<Schema.Kind> , ZTronSearchToken<Schema> .
Heterogeneous item types share the schema; each item declares its kind and the
subset of filter cases it uses.
Only raw strings are persisted: the kind as Kind.rawValue , filters as FilterRecord .
Typed cases are rebuilt with Kind(rawValue:) and Filter.init?(key:value:) at
query time. A document whose kind is unknown to the running build never surfaces as
a hit, and unknown filter records are ignored; both are logged, so an index written by
another app version never corrupts the enums.
Matching is equality on the record: AND across keys, OR among values of the same
key. {platform: ios, platform: mac, category: maps} means (ios or mac) and
maps.
The fallback filter carries both key and value because a single string would collapse
every ad-hoc filter into one dimension and lose those semantics.
Filters are never localized, never fuzzed and never prefix-matched; a token's display
label comes from the host.
This version matches on equality only; range filters (dates, numbers) would be a later
SearchRangeFilter protocol, not a new enum case.
5. Localization policy
When an item provides localized values, the engine indexes and matches those values for
the active locale; the base surface is only a fallback. This is normative for every channel.
1. Active locale. SearchEngineConfiguration.locale defaults to Locale.current and
is resolved to a BCP 47 tag once per index generation.
2. Field resolution. For each surface (title, text, keywords, caption) the projection takes
the first non-empty value in this order: exact tag match ( it-IT ), language match
( it ), base surface. Matching uses
Bundle.preferredLocalizations(from:forPreferences:) so fallbacks follow
Apple's rules.

3. Secondary languages. Surfaces for the other entries in Locale.preferredLanguages
are indexed into a low-weight localizedAlt field, so a query typed in a second
installed language still hits lexically. secondaryLanguages is .preferredLanguages
by default; .all and .none are available.
4. Normalization is per field language: NFKC, then folding(options:
[.caseInsensitive, .diacriticInsensitive, .widthInsensitive], locale:) .
The original string is kept for highlighting.
5. Tokenization uses NLTokenizer(unit: .word) with setLanguage(_:) from the
field's tag when known. Fields in scripts without word spacing (CJK, Thai) also emit
character bigrams so prefix matching works.
6. Fuzzy and prefix matching run over the normalized localized tokens, never over the
base surface alone.
7. Locale change. NSLocale.currentLocaleDidChangeNotification or an explicit
setLocale(_:) rebuilds the projection and lexical index in the background under a
new generation; in-flight and new searches keep using the old index until the swap.
Budget: 2 s for 100k items.
8. Semantic. Item vectors are computed from the base-language composition at build or
sync time, and the multilingual model carries cross-language matching. A pipeline may
ship per-locale vector sets; the engine then loads the active-locale set with base
fallback and never re-embeds items on device.
9. Filters, dates and numbers are compared in canonical form, never through localized
formatting.
10. Query language is not required. NLLanguageRecognizer may hint the normalization
locale for queries of 8 or more characters; otherwise the active locale applies.
11. Hits report matchedLanguage and matchedField , so the UI can highlight the localized
surface that actually matched.
12. Database fields (section 9.2). A string field declared as a localization key is resolved
through LocalizedStringResolving in the same order (exact tag, language, base)
and feeds localizedAlt the same way; a literal field carries the language tag the
host declared. The resolver is the only place a bundle is consulted, and it is injected by
the host.
UI strings follow the same rule: the host passes a localized placeholder, token labels are
localized display text wrapped around canonical values, and the UI product ships its own
Localizable.xcstrings in Bundle.module for the few built-in strings (Cancel, Clear,
Searching, No results).

7.2 Fuzzy
Two stages: generate correction candidates, then rewrite or augment the query and
retrieve normally.
Allowed edits by normalized token length: 1 to 2 characters none, 3 to 5 characters
one edit, 6 or more two edits.
No expansion for IDs, URLs, model numbers, filter values, quoted phrases or token
chips.
At most 8 candidates per token, ranked by edit distance then document frequency; a
candidate's term weight is 1 / (1 + edits).
Distance is computed on normalized Unicode scalars after the folding in section 5, so
résumé and resume are the same token before fuzzing.
The channel operates on the vocabulary (200k terms), never on documents, which
bounds both time and memory.
7.3 Semantic
Item vectors come from one deterministic composition, type + title + tags +
short description + caption , encoded once at build or sync time with the same
pinned model used for queries. The vector store records model id, dimensions and
quantization.
At query time only the query is encoded; HNSW returns the top 50 with M = 16 and
efSearch = 64.
The model is a shared multilingual space exported to Core ML with 8-bit weights, at
most 384 dimensions and a 128-token input window, verified to load on iOS 15.8. A9
has no Neural Engine, so every budget assumes CPU inference.
EmbeddingProvider is a protocol, so the model is swappable and tests use a
deterministic fake.
Distance kernels use Accelerate or simd ; no per-element Swift loops in the hot path.
7.4 Cross-encoder rerank, capable devices only
A cross-encoder scores each (query, candidate) pair with a full transformer pass, so its
cost grows with the candidate count and nothing can be precomputed. It runs wherever a
calibration pass proves it fits the budget, and never on the reference device.
Capability gate, SearchEngineConfiguration.reranking , default .auto :
.auto runs a one-time calibration on first use: rerank 16 synthetic pairs with the
production model and enable only when the p95 per pair is 15 ms or less, physical
memory is at least 3 GB and no memory warning occurred in the last 10 minutes. The

The A9 fails calibration by design (no Neural Engine, 2 GB). The gate is expected to

Stage:
Input: the top 16 fused hits of the semantic snapshot (configurable, at most 32), each
paired with the query and the hit's localized surface (title plus caption, or the first 64
tokens of text), truncated to 128 tokens per pair, scored in one batched call.
Model: a multilingual cross-encoder exported to Core ML with 8-bit weights, 6 layers
or fewer, 60 MB or less after vocabulary pruning.
Output: final score = 0.7 × normalized cross-encoder score + 0.3 × normalized RRF
score ( RankingProfile.rerank.blend ), so one confident pass cannot push an exact-
title hit out of the head.
Only the reranked head is reordered; hits below position 16 keep their fused order.
Published as a third snapshot ( phase: .reranked , isFinal: true ); on these
devices the semantic snapshot is no longer final.
Skipped, with degraded set, when the semantic phase was skipped, when the query
is tokens only, or when the 400 ms hard cap is breached. Three consecutive breaches
disable the stage for the session and force recalibration at the next launch.
The reranker loads lazily and unloads with the embedding model after 60 s idle; both
models are resident at once only on devices that passed calibration (section 15.2).
8. Fusion and ranking
Channels are combined by weighted Reciprocal Rank Fusion, never by adding raw scores.
s(d) = \sum_{c \in C} w_c \cdot \frac{1}{k + r_c(d)}
r_c(d) is the 1-based rank of document d in channel c ; a channel that did not return d
contributes 0. k = 60. Default channel weights: lexical 1.0, fuzzy 0.6, semantic 0.8. Weights
are tuned only against relevance judgments or interaction data, never by hand on
anecdotes.

Snapshot semantics:
1. The first snapshot ( phase: .lexical ) carries lexical and fuzzy hits fused by RRF and
arrives within the lexical budget.

direct Damerau-Levenshtein against each token with a length pre-check, prefix

11. Concurrency and liveness
The package compiles in Swift 6 language mode, so complete concurrency checking is on
and every public type is Sendable . The rules below are what the compiler cannot enforce.
Rules:
1. Mutable index and search state lives in actors: LexicalIndex , SemanticIndex ,
SearchService . UI models are @MainActor .
2. Structured tasks wherever a task's lifetime is scoped to a search; Task.detached
only for index loading at .utility priority.
3. A newer query cancels the prior task before any work starts on the new one.
4. Cooperative cancellation: Task.sleep(nanoseconds:) for debounce,
Task.checkCancellation() at least every 1,000 postings in scoring loops and every
100 node visits in HNSW.
5. Actor reentrancy is guarded by a generation counter: every await inside
SearchService is followed by a generation check before state is touched.
6. The UI boundary checks both generation and query equality before publishing a
snapshot.
7. Never block the cooperative thread pool: no semaphores, Thread.sleep ,
DispatchGroup.wait or synchronous actor hops. The only synchronous file calls are
the memory-map open and close.

14.4 Device gate and lifecycle
Gate ( ChatConfiguration.availability , default .auto ); all of the following must hold:
OS at least descriptor.minimumOS (iOS 17 for the MLX runtime) and physical
memory at least descriptor.minimumPhysicalMemory (6 GB for Qwen3-1.7B-4bit: 968
MB of weights plus KV cache and runtime, about 1.8 GB resident).
Free disk at least twice asset.totalBytes before a download starts.
A one-time calibration after the first load: prefill 512 tokens and decode 64; enable
only when time to first token is 3 s or less and decode runs at 8 tokens/s or more. The
verdict is persisted and recomputed after an app or OS update.
The iPhone 6s fails on OS and memory: chat is unavailable(.device) and the UI
shows no entry point. .on and .off override the gate for QA builds.
Fetching is a no-op when the files are already on disk and verified; a retry re-verifies and
resumes instead of starting over; an unload keeps the files and the session's history, so
the next message only reloads the weights.
Download policy: .wifiOnly by default, .allowCellular , or .never when the host pre-
bundles the files. The UI discloses the size (968 MB) before the first fetch; downloads
continue in the background through ZTronAssetKit's own session, and the engine only

15.5 Degradation policy
When a stage breaches its hard cap, the channel is skipped for that snapshot and
reported in SearchSnapshot.degraded ; the lexical snapshot is never withheld. After 3
consecutive semantic breaches, or a memory warning, the semantic channel is disabled
for the session and re-enabled on the next foreground. A rerank that breaches 400 ms is
skipped and the fused order stands; 3 consecutive breaches disable the stage for the
session and force recalibration at the next launch. A model that cannot meet its budget
(80 MB embedding, 60 MB reranker) is not shipped: the engine runs the channels it can
afford until a smaller model qualifies.

The design doc reports the lexical path, the field and the models as implemented or

Already implemented or specified: minimal Searchable and capability protocols,
