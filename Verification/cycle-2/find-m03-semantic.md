## Findings, most severe first

### C2-m03-semantic-01 — Model budgets are enforced on disk (in MiB), not as the resident memory section 15.2 budgets
- Severity: high. Category: spec-deviation. Spec: 15.2 (Memory, resident: "Embedding model, loaded 80 MB", "Reranker model, loaded 60 MB", "Peak during a semantic query, reference device 200 MB"), 15.5, 7.3/7.4.
- Locations: Sources/ZTronSearchEngineSemantic/SemanticError.swift:79-82; CoreML/CoreMLEmbeddingProvider.swift:148-153; CoreML/CoreMLCrossEncoder.swift:137-138; Scripts/semantic/ztron_conversion.py:32-33, 368-377, 455-457; Scripts/semantic/convert_embedding_model.py:124, 130; Tests/ZTronSearchEngineSemanticTests/CoreMLAdapterTests.swift:182-209.
- Description: `SemanticLimits.embeddingModelBudget`/`rerankerModelBudget` are documented as "On-disk budget ... (specification section 15.5)" and are compared with `FileAccess.footprintBlocking(of:)` of the `.mlmodelc` directory before load. Section 15.2 lists the 80 MB / 60 MB figures under "Memory (resident, search subsystem)" as "model, loaded". The default conversion route (`--format neuralnetwork`, the only one allowed for the iOS 15 floor) stores "8-bit linear" weights that, per the script's own docstring (ztron_conversion.py:374), "are expanded when the model loads". So the quantity checked (INT8 bytes on disk) understates the quantity budgeted (resident bytes of the loaded model) by the expansion factor, and nothing in the package or its tests measures the loaded model's resident size, the 200 MB semantic-query peak, or the 800 ms reload. The constants are also MiB (80 x 1024 x 1024 = 83.9 MB) while the spec says MB, and the script's `--budget-mb` prints MiB as "MB".
- Evidence: SemanticError.swift:79 `/// On-disk budget of the embedding model (specification section 15.5).`; :80 `80 * 1024 * 1024`; CoreMLEmbeddingProvider.swift:150-152 `let bytes = try loader.footprint(configuration.modelURL); guard bytes <= configuration.sizeBudget`; ztron_conversion.py:373-374 "neuralnetwork (the default) ... Weights are stored as 8-bit linear and expanded when the model loads"; ztron_conversion.py:456 "Fails when the shipped artifact is over its on-disk budget". The tests only script a footprint closure (81 MB vs 80 MB) and assert the constants.
- Failure scenario: a converted multilingual model of 79 MB on disk passes the gate and loads; once its weights are expanded at load it occupies a multiple of that resident on the CPU-only reference device, far beyond the 80 MB loaded budget and the 200 MB peak, and nothing reports it. The milestone 5/6 gates ("model within the 80 MB budget", "within 60 MB") are claimed by a check of a different quantity.

### C2-m03-semantic-02 — QuantizedVectorStore.build writes out of bounds when the given quantization has more dimensions than the space
- Severity: medium. Category: bug. Spec: 7.3 (INT8 store), API contract of `build`.
- Locations: Sources/ZTronSearchEngineSemantic/Vector/QuantizedVectorStore.swift:146-200 (172, 187, 194); Vector/VectorQuantization.swift:182-195.
- Description: `build(from:modelID:dimensions:quantization:)` validates every vector against `dimensions` but uses a caller-supplied `quantization` without checking `quantization.dimensions == dimensions`. It then calls `parameters.encode(valueBase, into: target, scratch: workBase)` (line 187), which runs vDSP over `parameters.dimensions` elements: it reads past the vector, writes `parameters.dimensions` floats into the `dimensions`-float scratch array and `parameters.dimensions` codes into the `ids.count * dimensions` code array. The dimension check that would throw `dimensionMismatch` only happens afterwards, in the staging initializer (line 194). The doc promises `dimensionMismatch` for vectors that do not fit the space.
- Evidence: scratch program vec/main.swift, scenario `b`: `QuantizedVectorStore.build(from: [("a",[1,0,0,0]),("b",[0,1,0,0])], modelID: "m", dimensions: 4, quantization: .uniform(dimensions: 384))` exited with status 139 (SIGSEGV) in 3 of 3 runs and under libgmalloc; the crash report puts the fault in `swift_release_dealloc` called from `static QuantizedVectorStore.build(from:modelID:dimensions:quantization:)`. Scenario `b2` calls the same `encode(_:into:scratch:)` with buffers sized as `build` sizes them inside guarded allocations and printed "bytes written past the 8-byte codes buffer: 376" and "bytes written past the 16-byte scratch buffer: 1520". `QuantizedVectorStoreTests.testBuildRefusesVectorsThatDoNotFitTheSpace` only tests the mismatch on `QuantizedVectorStore(modelID:dimensions:quantization:)`, not on `build`.
- Failure scenario: a host or pipeline that builds a vector file with a quantization fitted for another model width (e.g. reusing a 384-dimension quantization for a 256-dimension model) corrupts the heap and crashes instead of getting `dimensionMismatch`. The only internal caller (SemanticIndex.create) passes a matching quantization, so reach is the public API.

### C2-m03-semantic-03 — A large `limit` crashes or pins unbounded scratch memory in the HNSW search
- Severity: medium. Category: bug. Spec: 10 (bounded work), 15.2.
- Locations: Sources/ZTronSearchEngineSemantic/HNSW/HNSWGraph.swift:192-194; HNSW/HNSWWorkspace.swift:206-218; HNSW/HNSWIndex.swift:227-246; SemanticIndex.swift:152-161.
- Description: `HNSWGraph.search` sets `breadth = max(ef, limit)` and sizes the workspace with `ef: max(breadth, efEntry)`; `HNSWWorkspace.reserve` computes `ef + 2` and allocates `2 * listCapacity + ...` entries plus `listCapacity` node slots, never capped by the node count, and never shrinks them again. Neither `SemanticIndex.nearest(to:limit:)` nor `HNSWIndex.search` bounds `limit` (the exhaustive path does: `TopMatches(limit: min(limit, liveCount))`, QuantizedVectorStore.swift:592).
- Evidence: scratch program vec/main.swift over an index of 200 vectors: scenario `c`, `search(query, limit: Int.max)`, exited with status 133 (SIGTRAP); the crash report shows the trap in `HNSWWorkspace.withScratch(quantization:nodeCount:ef:_:)` (inlined `reserve`, `ef + 2` overflow) called from `HNSWGraph.search`. Scenario `c2`, `limit: 50_000_000`, returned 200 matches after 0.18 s with the process footprint at 956.4 MB, and a later search with limit 10 left it at 956.4 MB (peak footprint 1,002,915,088 bytes by /usr/bin/time -l).
- Failure scenario: a host that asks the semantic index for "everything" (`nearest(to:limit: Int.max)`) crashes the app; a host that sets `SearchLimits.semanticNeighbours` high (only clamped to >= 1) makes every semantic query allocate and keep scratch proportional to the limit instead of the corpus.

### C2-m03-semantic-04 — WordPiece files continuation pieces that start with a combining mark as word-initial pieces, so words that need them become [UNK]
- Severity: medium. Category: bug. Spec: 7.3/7.4 (multilingual models, 128-token window), 15.3 (non-Latin language in the golden set).
- Locations: Sources/ZTronSearchEngineSemantic/Tokenization/WordPieceTokenizer.swift:121-122; Tests/ZTronSearchEngineSemanticTests/WordPieceTokenizerTests.swift:6-15.
- Description: the initializer splits the vocabulary with `entry.piece.hasPrefix(prefix)` and `dropFirst(prefix.count)`, which compare Swift `Character`s (grapheme clusters). In a piece such as "##" + U+0902 (Devanagari anusvara) or "##" + U+093F (vowel sign i), the second "#" and the mark form one grapheme, so `hasPrefix("##")` is false and the piece goes into the initial table, where no word can ever reach it (BERT pre-tokenization splits "#"). Every word whose segmentation needs such a continuation becomes a single [UNK]. Multilingual WordPiece vocabularies (mBERT, DistilmBERT, LaBSE) hold many "##" + Indic vowel sign / Thai / Arabic mark pieces. The tests only use "##é" (one precomposed scalar).
- Evidence: scratch program tok/main.swift (product Tokenization files) printed `hasPrefix("##") on "##\u{0902}": false`, `Characters: 2 scalars: 3`, the same for U+093F and Thai U+0E31, then with vocabulary ["[PAD]","[UNK]","[CLS]","[SEP]","क","##ं","##ि"]: `tokenize("\u{0915}\u{0902}") = [1] expected [4, 5]`, `tokenize("\u{0915}\u{093F}") = [1] expected [4, 6]`, and with the default (uncased, accent-stripping) options `tokenize("\u{0915}\u{093F}") = [1]` (U+093F is Mc, which accent stripping keeps).
- Failure scenario: with a WordPiece multilingual embedding model or cross-encoder (both supported by TokenizerLoader and the conversion scripts), Hindi "कि"/"हिंदी"-style words, Thai and many Arabic words embed as [UNK]: queries and items in those scripts collapse to near-identical vectors. The default conversion model (paraphrase-multilingual-MiniLM-L12-v2, Unigram) is not affected.

### C2-m03-semantic-05 — A cancelled upsert leaves vectors in the index that the bookkeeping does not know; they are dropped at the quantization refit or not carried at a locale switch
- Severity: medium. Category: concurrency. Spec: 7.3 (runtime upserts), 5 rule 8 / 17 (per-locale sets), 11 (cancellation).
- Locations: Sources/ZTronSearchEngineSemantic/SemanticIndex.swift:413-439 (425-426, 429, 433-436); HNSW/HNSWIndex.swift:178-193; core call site Sources/ZTronSearchEngine/Service/SearchService.swift:258-265.
- Description: `store(_:)` calls `index.insert(contentsOf: entries)`, which checks cancellation every 128 insertions and leaves what it inserted ("what was inserted until then stays"). When it throws, `store` skips `provisionalVectors = all` (provisional path) and the `upsertedAtRuntime`/`removedAtRuntime` updates (catalog path). The provisional refit (`create(from: all...)`) rebuilds the set only from `provisionalVectors` + the new entries, so the partially inserted vectors vanish; with per-locale sets, `setLocale` carries only `upsertedAtRuntime`, so they are left behind. Core's `upsertVectors` reports the CancellationError as "item vectors were refused", which reads as "nothing stored".
- Evidence: scratch program idx/main.swift (product SemanticIndex, HNSW and Vector files): upsert 10 vectors; upsert 200 in a task cancelled at once -> "threw CancellationError", "count 138; contains(cancelled-000) true"; upsert 120 more -> count 258; upsert 130 more (refit at 256) -> "count 260; contains(cancelled-000) false". 128 vectors disappeared without a removal.
- Failure scenario: the host indexes a batch of more than 128 items from a task that is cancelled (view disappears, sync cancelled). The semantic channel keeps them for a while, then silently loses them at the next refit or locale switch; those items stop being reachable by cross-language queries while lexical search still finds them.

### C2-m03-semantic-06 — The "Not a gate" isotropic HNSW test enforces the latency gate and turns the CI quality-targets step red
- Severity: medium. Category: test-integrity. Spec: 15.1 (HNSW ANN top 50, 5 ms p95), 16.
- Locations: Tests/ZTronSearchEngineSemanticTests/HNSWRecallTests.swift:117-127, 218-226; .github/workflows/ci.yml:53-56.
- Description: `testRecallOnIsotropicTopicsIsReportedAndRecoversWithBreadth` is documented as "Not a gate" and runs `measure(..., efSearch: 256)`, four times the specification's breadth; `measure()` unconditionally asserts the scaled 5 ms budget (`XCTAssertLessThan(measurement.coldP95, allowed, ...)`) on every call. A documentation run therefore fails the suite, and the CI step "HNSW recall and latency at 100,000 vectors" (ZTRON_SEMANTIC_LARGE=1) cannot be green on a machine where an efSearch=256 search exceeds 0.833 ms p95, which hides the real gates' status. The real 100k gates pass with ~1% margin (cold p95 0.822 and 0.823 ms against 0.833 ms).
- Evidence: Verification/_runs/c2-release-semantic-large.log:137 `XCTAssertLessThan failed: ("0.0009419170091859996") is not less than ("0.0008333333333333334") - top-50 search, cache-cold p95`, EXIT 1; c2-release-hnsw-recall-rerun.log:37 the same test fails with 0.0009524, "Executed 6 tests, with 1 failure", EXIT 1; log line 426/51: efSearch=256 cold p95 0.942/0.952 ms.
- Failure scenario: CI's quality-targets job fails on a non-gate measurement; a reader cannot tell from the job status whether recall@10 >= 0.95 and the 5 ms ANN gate hold.

### C2-m03-semantic-07 — Vector and graph files with tombstone bits beyond the row/node count are accepted; rows appended later are born tombstoned
- Severity: low. Category: bug. Spec: 7.3 (memory-mapped vector and graph files), hostile/damaged file handling.
- Locations: Sources/ZTronSearchEngineSemantic/Vector/QuantizedVectorStore.swift:275, 292-294, 513-532; HNSW/HNSWGraph.swift:378, 423-424, 126-137; HNSW/HNSWIndex.swift:80-82; Support/BinaryCoding.swift:247-249.
- Description: both decoders compare the live/deleted count with `Bitset.population`, which counts every bit of every word, including the bits above the row/node count in the last word; nothing requires those bits to be zero. `HNSWIndex(store:graphAt:)` compares tombstones only for `0..<store.count`. A file with such a bit (and the count adjusted to match) is accepted with a phantom tombstone; the next appended row/node lands on that bit (`upsert` appends at `count`, `HNSWGraph.insert` only `reserve`s words) and is tombstoned from birth.
- Evidence: scratch vec/main.swift scenario `f` (vector file, bit 50 of 50 rows, live count 49): "crafted file accepted: count 50, liveCount 49, ids.count 50, tombstoneCount 1"; after `upsert("late")`: "ordinal 50; contains(late) true; vector(for: late) nil; ids contains late false", and exhaustive nearest to its own vector does not return it. Scenario `g` (graph file, bit 50 of 50 nodes, deleted count 1): "crafted graph accepted: count 50, tombstoneCount 1"; after `insert("late")`: contains true, HNSW search for its own vector returns item-18/29/15, exhaustive search returns "late 1.000" first.
- Failure scenario: a damaged or crafted shipped/saved file makes the next runtime vector(s) invisible to search while `contains` says they are stored. The package's own writer never sets those bits, so reach is damaged or hostile files.

### C2-m03-semantic-08 — Id identity differs between the mapped rows (bytes) and the in-memory overlay (canonical equivalence)
- Severity: low. Category: bug. Spec: 7.3 (vector store keyed by SearchableID).
- Locations: Sources/ZTronSearchEngineSemantic/Vector/QuantizedVectorStore.swift:430-434, 683-700, 156-170; Sources/ZTronSearchEngine/Contracts/Searchable.swift:9-38 (synthesized Hashable over String).
- Description: `SearchableID` equality is `String` equality (canonical equivalence), but `ordinal(of:)` looks base rows up by a byte-wise binary search, while the overlay and `build`'s de-duplication use a Swift dictionary. An id stored in the file as NFC is not found under its NFD spelling, so an upsert of the NFD spelling appends a second live row for an id that compares equal, and `remove` of the NFC spelling retires the appended row (found through the overlay) and leaves the base row live.
- Evidence: scratch vec/main.swift scenario `o`: "SearchableID NFC == NFD: true; same hash: true"; "contains(NFC) true; contains(NFD) false"; upsert(NFD) -> "ordinal 2, replaced nil; liveCount 3"; "3 rows, 2 distinct SearchableIDs"; "remove(NFC) retired ordinal Optional(2); contains(NFC) afterwards true".
- Failure scenario: ids carrying non-ASCII text from two sources with different normalization get duplicate semantic rows and a removal that does not take; core's resolve hides most of it, so the effect is mostly wasted neighbour slots and a stale vector.

### C2-m03-semantic-09 — TokenizerLoader approximates where its contract says it refuses
- Severity: low. Category: false-claim. Spec: 7.3/7.4 (the model's own tokenization).
- Locations: Sources/ZTronSearchEngineSemantic/Tokenization/TokenizerLoader.swift:124-128, 236-270 (264-268), 294-296, 305-306, 337-338, 359-406; Tokenization/TextNormalization.swift:15-21.
- Description: the doc says "An unsupported file is refused rather than tokenized approximately", but: `model.byte_fallback` is never read (a byte-fallback Unigram model gets `<unk>` where the reference emits byte pieces); every `Precompiled`/`Nmt` normalizer is replaced by an NFKC reproduction whatever the charsmap holds (an `nmt_nfkc_cf` or identity map is tokenized differently); a WordPiece file with `"normalizer": null` gets uncased BERT normalization (lowercase + accent stripping), where the reference applies none (the Unigram branch correctly uses identity); an unknown post-processor type returns `nil` and silently falls back to a default template; `Sequence` entries without a `type` are dropped by `compactMap`.
- Evidence: code as cited; `grep byte_fallback` finds nothing in Sources/ZTronSearchEngineSemantic; the TokenizerLoaderTests compare the loader against the same Swift tokenizers, never against reference token ids.
- Failure scenario: a model whose tokenizer.json uses any of these features loads without error and produces token ids that differ from what it was trained on, degrading embeddings without a diagnostic.

### C2-m03-semantic-10 — Items embedded on device get the query prefix
- Severity: low. Category: bug. Spec: 7.3 (deterministic item embedding text, query-only runtime encoding).
- Locations: Sources/ZTronSearchEngineSemantic/SemanticIndex.swift:269; CoreML/CoreMLEmbeddingProvider.swift:36-38, 125-127; EmbeddingProvider.swift (single `encode`); Scripts/semantic/convert_embedding_model.py:123.
- Description: `embedMissing` embeds item text through `encodeQuery`, and `CoreMLEmbeddingProvider.encode` always prepends `configuration.queryPrefix` ("Text put in front of every query ... `query: ` for the multilingual-e5 family"). The protocol has no way to ask for a passage embedding, so on-device item vectors carry the query prefix while pipeline vectors would carry the passage form.
- Evidence: SemanticIndex.swift:269 `pending.append((id, try await encodeQuery(text, locale: locale)))`; CoreMLEmbeddingProvider.swift:126 `[configuration.queryPrefix + text]`.
- Failure scenario: with an e5-style model configured with `queryPrefix: "query: "`, items embedded by `embedMissing` live in a different region than shipped item vectors, so ranking differs between shipped and on-device items. No effect with the default (empty) prefix.

### C2-m03-semantic-11 — Switching to a locale whose set is unusable reloads (and may rebuild) the base set every time, then discards it
- Severity: low. Category: performance. Spec: 10 (throttling and memory), 5 rule 8.
- Locations: Sources/ZTronSearchEngineSemantic/SemanticIndex.swift:208-234 (210, 218), 377-405 (385-389, 404).
- Description: `setLocale` proceeds when `catalog.resolve(tag).languageTag != activeSet`; `load` falls back to `open(catalog.base)` when the localized set fails; when the base is already active, `guard loaded.languageTag != activeSet` discards the result. Each call re-maps the base files, and when the base ships without a graph file, `HNSWIndex.build(over:)` rebuilds the whole graph (about 1 ms per vector on the reference device by the type's own doc) only to throw it away, while `exclusively` holds back every upsert and removal.
- Evidence: code as cited (traced, not run).
- Failure scenario: a damaged `vectors.de.ztvec` plus a base set without `.zthnsw`: every locale change to German costs a full graph build (minutes at 100k vectors on the reference device) and blocks runtime changes meanwhile.

### C2-m03-semantic-12 — Removals are only recorded for ids present in the active set
- Severity: low. Category: bug. Spec: 5 rule 8 / 17 (per-locale vector sets).
- Locations: Sources/ZTronSearchEngineSemantic/SemanticIndex.swift:189-202, 222-224.
- Description: `remove` adds to `removedAtRuntime` only the ids the current set held (`index.remove(contentsOf:)` returns those). An id that exists only in another locale's set is not recorded, so it is live again after `setLocale` switches to that set.
- Evidence: code as cited (traced, not run). Core's `resolve` drops ids it no longer indexes, so the visible effect is limited to wasted neighbour slots and `contains`/`count`.
- Failure scenario: item present only in `vectors.it` is removed while the base set is active; after switching to Italian, `contains` is true again and it occupies semantic neighbour slots.

### C2-m03-semantic-13 — Constrained queries ask HNSW for 200 neighbours; spec 10 bounds the work at 50 and the ANN gate is only measured at 50
- Severity: low. Category: spec-deviation. Spec: 10 ("50 HNSW neighbours"), 7.3 (top 50, efSearch 64), 15.1.
- Locations: Sources/ZTronSearchEngine/Service/SearchService.swift:552-558, 567 (core call site); Sources/ZTronSearchEngineSemantic/HNSW/HNSWGraph.swift:192; Contracts/SearchEngineConfiguration.swift:33-36.
- Description: a query with filters or phrases requests `min(n*4, max(n,200))` = 200 neighbours; `breadth = max(ef, limit)` turns that into an ef-200 bottom-layer search. Documented in `SearchLimits`, but it deviates from the bounded-work rule, and `HNSWRecallTests` measure latency only at limit 50 (efSearch 256 already measured 0.94-0.95 ms cold p95 against the 0.833 ms scaled budget).
- Evidence: SearchService.swift:558; HNSWGraph.swift:192; run logs cited in finding 06.
- Failure scenario: constrained semantic queries on the reference device do roughly three times the ANN work of the budgeted query and are not covered by the 5 ms gate.

## Checked and knocked down

- Damaged graph links read without validation in `HNSWOperation.connect`/`select` during insertion: not reachable. Every node a layer search returns was popped and expanded, and expansion validates every link of its block (`guard neighbour < graph.nodeCount ...`), so `connect` only reads validated blocks.
- Quadratic copy-on-write in `embedMissing` (store snapshots held across inserts): measured with idx2/main.swift, embedMissing vs batched upsert: n=4,000 0.29/0.27 s, 8,000 0.72/0.66 s, 16,000 1.59/1.56 s, 32,000 3.77/3.75 s. Linear, no finding.
- Vector and graph reader/writer agreement, section alignment, bounds checks in BinaryReader, heap and workspace sizing for normal limits, vDSP argument order, asymmetric quantized dot product, PairTruncation closed form, Unigram Viterbi against the HF algorithm, calibration thresholds (16 pairs, nearest-rank p95 <= 15 ms, >= 3 GB rounded, 10-minute warning window, verdict keyed by model and app/OS fingerprint), core hard-cap race, idle unload and memory-warning handling: no defect found.
- 100k recall gates: pass (recall@10 0.994/0.9996 against INT8 brute force, 0.982 against Float), latency gates pass narrowly on a loaded host.
