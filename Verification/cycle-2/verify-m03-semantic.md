### C2-m03-semantic-02 — build() writes out of bounds with a wider quantization
- Verdict: confirmed. Severity: medium.

- Repro (scratch f02/main.swift, product files copied verbatim, `swiftc -O -swift-version 6`):

### C2-m03-semantic-04 — WordPiece misfiles "##" + combining-mark pieces
- Verdict: confirmed. Severity: medium.
- Trace: `WordPieceTokenizer.init(entries:...)` (WordPieceTokenizer.swift:117-126) splits the vocabulary with `entry.piece.hasPrefix(prefix)` / `dropFirst(prefix.count)`, both on `Character`s. A mark extends the grapheme of the preceding "#", so "##" + mark is two Characters and `hasPrefix("##")` is false; the piece lands in `initial`. `split` (lines 148-187) walks Unicode-scalar boundaries and looks continuations up in `continuation` only, so any word whose segmentation needs a mark-initial continuation becomes one `[UNK]` (lines 178-182). Both the `vocab.txt` initializer (line 77) and the tokenizer.json path use this designated initializer. The Hugging Face WordPiece model prepends "##" to the substring and looks the string up, so the reference finds these pieces.
- Repro (scratch f04/main.swift, product Tokenization files): `hasPrefix("##")` is false for "##"+U+0902, U+093F, U+0E31, U+064E (Characters 2, scalars 3) and true for "##"+U+00E9 and "##"+U+0930. With vocabulary [PAD, UNK, CLS, SEP, क, ##ं, ##ि, हि, ##ंदी, ##र] and cased options: tokenize(U+0915 U+0902) = [1] (reference [4, 5]); tokenize(U+0915 U+093F) = [1] (reference [4, 6]); tokenize("हिंदी") = [1] (reference [7, 8]); control tokenize("कर") = [4, 9]. Uncased (default, accent stripping): U+0915 U+0902 = [4] (the Mn mark is stripped), U+0915 U+093F = [1] (Mc is kept).
- Reach: any WordPiece vocabulary with mark-initial continuation pieces; the default conversion model is Unigram and unaffected, and the embedding script refuses hidden sizes over 384, which excludes most multilingual WordPiece models (mBERT, DistilmBERT, LaBSE). The cross-encoder script has no width limit, so a 6-layer DistilmBERT-style reranker is a realistic WordPiece candidate. Medium stands for a supported configuration that silently degrades non-Latin text (15.3 requires a non-Latin language).

Low: a state-consistency defect confined to an operation that already reported failure.

### C2-m03-semantic-01 — model budgets enforced on disk, not as resident memory
- Verdict: partly. Severity: medium (auditor: high).
- Code facts, all confirmed: `SemanticLimits.embeddingModelBudget`/`rerankerModelBudget` are `80 * 1024 * 1024` / `60 * 1024 * 1024`, documented as "On-disk budget ... (specification section 15.5)" (SemanticError.swift:79-82). Both adapters compare `loader.footprint(modelURL)` with `sizeBudget` before loading (CoreMLEmbeddingProvider.swift:148-153, CoreMLCrossEncoder.swift:137-141), and `FileAccess.footprintBlocking` sums file sizes under the `.mlmodelc` (FileAccess.swift:35-60). ztron_conversion.py:373-374 says the default `neuralnetwork` route stores weights "as 8-bit linear and expanded when the model loads". The `mlprogram` route is refused below iOS 16, so the iOS 15.8 reference device only has the expanding route. `enforce_budget` (455-465) prints MiB as "MB". The tests script a footprint closure only (CoreMLAdapterTests.swift:180-209). The 15.2 constants in ZTronSearchFixtures/ReferenceDevice.swift:78-84 (`embeddingModelBytes`, `rerankerModelBytes`, under "15.2 Memory, resident") are referenced nowhere. No test or tool measures a loaded model's resident size, the 110 MB steady state, the 200 MB semantic-query peak or the 800 ms reload (grep over Sources and Tests).
- Spec: 15.2 lists "Embedding model, loaded 80 MB; reload after unload 800 ms or less" and "Reranker model, loaded ... 60 MB" under "Memory (resident, search subsystem)", and 16 asks for "resident memory assertions from section 15.2". So the loaded-memory target is required and nothing verifies it. But 15.5 ("A model that cannot meet its budget (80 MB embedding, 60 MB reranker) is not shipped") does not say which quantity. 7.4 frames the reranker as "60 MB or less after vocabulary pruning", and 17's open question asks which model "fits 80 MB after 8-bit quantization and vocabulary pruning". Both are artifact-size framings.
- Why partly: the gap is real. The on-disk check does not show the 15.2 loaded target is met, and with weights expanded at load it can understate resident size by the expansion factor (about 4x if expanded to Float32 on the CPU; not measured here, since no model or device is available). But the on-disk gate is a legitimate implementation of the 7.4/17 size framing, not the wrong quantity for a requirement that asks for a runtime check: no section asks the adapter to enforce resident memory, and that cannot be done before load. The milestone 5/6 gates are not claimed. README.md:127-129 says "The package ships no model" and that model choice is an open question, and README.md:175-176 and 205-214 say only model-free section 15 targets are tested and only a device run settles a gate. The MiB-vs-MB point is cosmetic: every 15.2 budget in the package is binary and the spec does not define MB.
- Corrected description: the package checks only the model's on-disk size. It has no assertion or measurement of the loaded model's resident memory, the 200 MB peak or the 800 ms reload (a section 16 gap), and its docs and script present the on-disk figure as "the budget", although the iOS 15 conversion route expands weights at load. Medium: a missing verification of a release target that can only be closed on the device with a chosen model, not a runtime misbehaviour.

### C2-m03-semantic-07 — tombstone bits beyond the row/node count are accepted
- Verdict: confirmed. Severity: low.
- Trace: `QuantizedVectorStore.init(data:)` reads `(rowCount + 63) / 64` tombstone words and only checks `rowCount - tombstones.population == liveCount` (QuantizedVectorStore.swift:275, 292-295). `Bitset.population` counts every bit of every word (BinaryCoding.swift:247-249). `HNSWGraph.decode` does the same with `deleted.population == deletedCount` (HNSWGraph.swift:423-424). `HNSWIndex(store:graphAt:)` compares tombstones only for `0..<store.count` (HNSWIndex.swift:84-86). `upsert` appends at `ordinal = count` (QuantizedVectorStore.swift:523), and `HNSWGraph.insert` only `reserve`s words (HNSWGraph.swift:135), so a set bit at the next ordinal survives.
- Repro (f07/main.swift, product Vector/HNSW files; files written by the product, then patched):
  - f, vector file of 50 rows with row 10 removed (tombstone word 0x400), patched to bit 50: "crafted file accepted: count 50, liveCount 49, ids.count 50, tombstoneCount 1". `upsert(late)`: "ordinal 50; contains(late) true; vector(for: late) nil; ids contains late false; isTombstoned(50) true". The exhaustive nearest to late's own vector does not return it ("item-08 0.788", ...); the control on the honest file returns "late 1.000".
  - g, honest 50-row store plus its graph with bit 50 set and the deleted count set to 1: "crafted graph accepted: count 50, nodeCount 50, tombstoneCount 1". After `insert(late)`: contains true, count 51. HNSW search for its own vector returns item-08/18/32 while the exhaustive search returns "late 1.000" first. `validateGraph` reports the size disagreement.
  - Random damage, one bit flipped above the row count with the counts untouched: "refused: corrupt file: the tombstones of the vector file do not match its live count".
- Reach is as stated: the package's writers only set bits below `count` (`retire`, `markDeleted`, `words(covering:)`). A single random flip is caught by the population check, so it takes a coordinated edit of the bit and the count, which in practice means a crafted file. The effect is that the next runtime vector or vectors become invisible to search while `contains` reports them. Low.

### C2-m03-semantic-08 — id identity differs between mapped rows (bytes) and the overlay (canonical)
- Verdict: confirmed. Severity: low.

- Repro (f08/main.swift, product Vector/HNSW/SemanticIndex files):

### C2-m03-semantic-09 — TokenizerLoader approximates where its contract says it refuses
- Verdict: confirmed. Severity: low.
- Contract: TokenizerLoader.swift:126-128, "An unsupported file is refused rather than tokenized approximately." Each cited case was traced and, except the charsmap one, run (f09/main.swift, product Tokenization files, crafted tokenizer.json files). The Hugging Face library is not installed here, so reference ids were not computed. The reference behaviour below is the library's documented semantics.
  - `byte_fallback`: never read (grep over Sources/ZTronSearchEngineSemantic finds nothing). A Unigram file with `"byte_fallback": true` and the pieces `<0xC3>`/`<0xA9>` gives tokenize("a é") = [3, 4, 3, 0], with the unknown character as `<unk>` (0). The reference emits the byte pieces (5, 6).
  - `Precompiled`/`Nmt` map to `.sentencePiece` whatever the charsmap (305-306). TextNormalization.swift:15-21 itself says the map "is not interpreted" and is reproduced as NFKC plus SentencePiece's whitespace rules, so any other charsmap (case-folding, identity), or `Nmt` without NFKC, is tokenized approximately. Traced, not run.
  - WordPiece `"normalizer": null` falls back to `.bert(... stripAccents: true, lowercase: true)` (266-267): tokenize("Café") = [5] ("cafe"). With an explicit cased BertNormalizer it is [4] ("Café"), which is what the reference gives for a null normalizer (no normalization). The Unigram branch uses `.sequence([])` (231), as the auditor says.
  - Unknown post-processor type returns `nil` (405-406), and the WordPiece branch then wraps "cafe" as [2, 5, 3] ([CLS] ... [SEP]); the reference cannot load an unknown type at all. Related, and not in the finding: a Unigram `"post_processor": null` also falls back to `<s> ... </s>` (window [1, 3, 4, 2, ...]), where the reference adds no special tokens.
  - A `Sequence` normalizer entry without `type` is dropped by `compactMap` (296): accepted, tokenize("Café") = [4]. The reference rejects such a file.
- Tests: TokenizerLoaderTests asserts hand-computed ids over small synthetic vocabularies or compares with the Swift tokenizers themselves; no test uses ids produced by the reference tokenizer.
- Impact as stated: each case loads without a diagnostic and changes token ids. The default model's tokenizer (XLM-R Unigram, `nmt_nfkc` Precompiled map, TemplateProcessing, no byte fallback) uses none of them except the documented, near-exact NFKC reproduction. Low.

### C2-m03-semantic-10 — items embedded on device get the query prefix
- Verdict: confirmed. Severity: low.

- Repro (f10/main.swift: the full semantic module copied, the real `CoreMLEmbeddingProvider` with a scripted `SequenceModelLoader` whose fake model records its input ids, WordPiece vocabulary [PAD, UNK, CLS, SEP, query, :, red, apple, passage], `queryPrefix: "query: "`): `embedMissing([("item-1", "red apple")])` gives "the model received: [CLS] query : red apple [SEP]", identical to `encodeQuery("red apple")`.

The defect stands as described: on-device item vectors are encoded as queries, with no way to encode them as passages. No effect with the default empty prefix. Low.

- Verdict: confirmed. Severity: low.
- Trace: `setLocale` proceeds when `catalog.resolve(tag).languageTag != activeSet` (SemanticIndex.swift:211). `load` logs the failure of the localized set and returns `open(catalog.base)` (392-404), which re-maps the base and, when the base has no graph file, runs `HNSWIndex.build(over:)` (386-389). - Repro (f11/main.swift, product files; base of 5,000 64-d vectors, `vectors.de.ztvec` holding garbage):

- Impact as stated: it needs an unusable localized set, and the cost only matters when the base ships without a graph file. Then each locale change to that language costs a full graph build (about 1 ms per vector on the reference device, by HNSWIndex's own doc) and holds runtime changes back. Otherwise it costs a cheap re-map. Low.
